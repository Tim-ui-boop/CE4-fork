# r100 Test Button Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a launcher button "Test r100 randomizer" that writes a fixed, verified enemy-list sidecar proving r100 can be changed to island soldiers, archers, club carriers, JJ and regenerators.

**Architecture:** The offline enemy randomizer already writes private `etc/emleon0N.esl` copies and the core serves them via `runtime/enemy_sidecar.cpp`. This test reuses that path with a new fixed-deal method in `EnemyShuffle.java` and a new button in `MainActivity.randomizerSection`. No native change is needed: the sidecar accepts any id <= 0x60, and all four enemy kinds used by the test already exist on the retail disc.

**Tech Stack:** Java (Android launcher), 32-byte big-endian GameCube ESL records, GitHub Actions for the APK.

**Spec:** the approved design in chat on 24 Nov 2026 (button text, exact enemy mix, module budget, no disc/save writes).

## Global Constraints

- Button label must read exactly: `Test r100 randomizer`.
- Only `etc/emleon00.esl`, only records whose `room` field is `0x0100`, may change.
- Preserve `set`, `room`, `pos`, `rot`, `Character`, `Guard_r`, `be_flag` on every record; HP may change only on the five crow replacements.
- Module budget for r100 must stay at four kinds: `0x12` (hardcoded officer-killer), `0x1D` (island + JJ), `0x36` (regenerator), `0x21` (dog). No `0x2A` trap module may be needed.
- Discs, saves and other lists untouched. "Turn off" still removes the whole sidecar folder.
- Verify before writing: write to staging, read back, compare, promote, then write marker.

## Review Focus

- The import may lack `em/em1d.drs` or `em/em36.drs`; the test must report a clear message rather than a half-written set — pinned by the source-file/read validation step.
- A discarded normal deal must not leave the r100 test partially in place — pinned by staging and promotion steps.
- Counting mistakes (12 villagers / 5 crows / 7 traps) must refuse the whole test — pinned by exact-count assertions.
- The four-module budget must not be exceeded by leaving any trap record on `0x2A` — pinned by the verification step.
- Other rooms in `emleon00.esl` must not be touched — pinned by byte-for-byte verification outside room `0x0100`.
