# Offline randomizer: findings and next playable test

**Scope:** CubeEvil4, US retail GameCube `G4BE08`, story mode. Goal: one seed chosen in the launcher, before Start game, for rooms, items and enemies. Keep imports and saves untouched. PC randomizer data is a design reference, not a source of interchangeable GameCube records.

The existing [in-game enemy mod](../whole/runtime/enemy_random.cpp) is a separate system with its own seed and exclusions. It is not offline enemy-type replacement.

- **This test build:** Launcher → Randomizer → Advanced → Opening forest playtest. Enable the fixed seed-100 trial, then start a fresh game with runtime mods off. Disable it from the same control and restart to return to the ordinary collection. This is a test fixture, not yet a general enemy generator or a confirmed playthrough.

## Why these systems must be tested together

**Rooms.** [DoorShuffle.java](../android-decomp/app/src/main/java/com/ast/re4decomp/DoorShuffle.java) edits decoded copies (`randomizer/stN/rNNN.das.raw`). An AEV door specifies stage, room, part, arrival coordinates and facing. Transfer the whole destination; it neither moves geometry nor creates a return trigger. PC `MainPathRooms`, `PathSegments`, room classes and `Return` files describe both ends: the sample starts `r100 → r11a → r224` and sends the first return to the original `r100` landing. On GC use real triggers at both ends. A path to the correct room is not necessarily a path from the landing to the intended exit.

The all-gates-open story baseline is **96 rooms reachable forwards**; 97 counted a reverse-only connection. Don't use an undirected graph. Keep chapter-handover records, shooting range `r22c` and its five merchant rooms, player pins, and scenario exceptions `r11b` (previous room determines boat pier), `r10f` (gondola), `r208` (water hall). Treat reserved rooms as leaves, not a supply of rewritable exits. Keep `r309` and `r30a` in the pool. Test both entrances to `r309` before assigning a direction to its drop; the escape cutback is not an ordinary `r30a` transition. Patch 0240 bypasses the Ashley door check while `doors.active` exists; this is not proof that Ashley can follow a route.

**Items.** The [retail gate map](KEY-DOOR-MAP.md) covers 127 rooms across stages 1–4; the joint deal uses story stages 1–3. Of 1,607 authored ITA item areas, 133 wait on an enemy slot, 462 on a breakable object and 1,012 have neither owner. An ownerless area can still be enabled by a script. ITA defines the placement, amount and owner; ITM supplies pickup models/textures. [ItemShuffle.java](../android-decomp/app/src/main/java/com/ast/re4decomp/ItemShuffle.java) can add supported missing pickup models, not enemy or scenery assets. Watch room-pack growth across repeated deals.

The survey found 30 distinct item-use IDs across 23 rooms. Door lock kind and `key_flg` are **not** inventory IDs. Place a required key on a guaranteed pickup before its specific use. The current final walk credits IDs in reached rooms, and a room-level gate can block more exits than the real gate. Test the [r201 dungeon key `0xC3`](../../src/st2/r201.cpp): behind its own locked passage must fail; collectible beforehand must pass. Audit ID zero (not always empty), quantity-only writes, exclusion of pinned sources versus actual script grants, and save-state item flags.

**Enemies.** Eleven shared ESL lists (`emleon00–07`, `omake00–02`), not one per room. A slot's array index matters for scripted spawns, death flags and held items; don't reorder rows. [EmSetFromList](../../src/game/em_set.cpp) handles eligible room-entry actors. A room script can request a specific stored slot later, or construct an event actor directly. In [r100](../../src/st1/r100.cpp), 25 populated retail list rows include five crows enabled on entry; the ambush calls seven Ganado slots by number, and the house scene also constructs an actor itself. Protect those scripts' assumptions. Assigned drops are distinct from ordinary death-roll loot.

The [loader](../../src/game/read.cpp) has **four dynamic enemy-module slots** (`EmReadModule[4]`, `pullEmModule`). With no free slot, loading can return null. This is not four individual enemies, four visible models, or proof of a crash on a fifth model. Measure actual loaded modules on entry **and during events** before testing unrelated families. Patch 0242 reloads shared lists on backwards group crossings; some enemies may respawn. Patch 0241 guards positioning a missing actor, not the scripted mechanism that needed it. The PC tool uses curated slot exclusions and room-specific resource fixes. For example, PC `r111` offsets `0x1400` and `0x1440` correspond to live GC slots `0xA0`/`0xA2`, but their PC held items are not vanilla GC drops.

## After the first playable test

1. Compare the planned seed, actual written files and observed result on the first deal and repeat deals. Record build, seed, layout, entry, pickups, exit, first unmet requirement, `DoorShuffle` log and route report. Separate a pre-write refusal from an incomplete post-write check.
2. Stage outputs separately; re-read and validate before activation. Keep the previous playable set on failure. Use independent repeatable seed sequences for route, items and enemies so expanding one pool does not change the others.
3. Deal routes first, required pickups second, ordinary items/enemies last. Extend tests to gates at individual passages, entrance-dependent movement, scenario flags and chapter transitions. Start with `r201`, the two sides of `r309`, the lake and water hall. A graph verdict is never a completed campaign.
4. Expand enemy variation from same-family donors to **measured** compatible families only. Account for event waves, resource loads, slot ownership and persistence after backwards travel. Never count a required enemy drop as guaranteed without a demonstrated spawn, death, pickup and revisit.
5. Keep setup in the launcher before gameplay; hide legacy write-tests, retain their code, and separate delete/recollect from shuffling. Build test APKs with GitHub Actions. Do not commit retail data or imply CI played the game.
