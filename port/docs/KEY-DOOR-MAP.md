# Keys, doors and the room graph (read from the G4BE08 discs)
Generated by `.harness/analysis/gc_rooms.py survey` and `.harness/analysis/keymap.py`, which read the
disc images directly: the room archive (`StN/rNNN.das`), its Yz2 body (`tools/motion/yz2.py`), the `AEV` chunk
(header: magic, u16 version `0x104`, u16 count at `+6`, records at `0x10`, 0x9C bytes each) and the `ITA` chunk
(version `0x105`). Field offsets are the decomp's `include/sce_at.h`: `id` 0x35, door stage/room/part/key_id/
key_flg 0x6C..0x6F + 0x74, use item 0x5E, item id 0x78, count 0x7C.

Why this matters: a progression key is not a magic flag somewhere in the `.dol`. Every item-gated gate is an
`AEV` **use area** (SCEAT_ID_USE = 17) that names the item it needs, and every locked door is an `AEV` **door
area** (SCEAT_ID_DOOR = 1) that names a `key_flg` bit. Both live in the decoded room archive, i.e. in the
randomizer's own sidecar, so the same in-place byte patching that moves items can also move doors and gates.

## What the discs say
- rooms read: **127** (st1 29, st2 42, st3 42, st4 14; both discs)
- item-gated use areas: **30** ids in **23** rooms; every one of them is a physically placed item
- locked doors carrying a `key_flg`: **9**
- required keys that are never placed as a room item: **none**

## What this changes for the shuffle

1. **Keys can stay where they are and still be checked.** Because every key is placed somewhere and every gate
   names it, a seed can be validated: walk the graph from the start room, collect the items of the rooms that
   are reachable, and see whether the next gate's item is in hand before the gate is needed. That is the check
   the whole offline-sidecar design was chosen for.
2. **A key must never be dealt by the general shuffle.** The pool already keeps the ids above out (they are on
   the `KEYS_AND_FILES` list), and `typetable.py` showed the eight `itemInfo` type-11 ids are merchant gear
   (maps, attaché cases, vests), not keys — so the type filter was never the right test. The gate table here is.
3. **Door randomization is a second patch on the same record set.** A door area's destination is three bytes
   (`0x6C` stage, `0x6D` room, `0x74` part) and its far position is three floats at `0x5C`. Rewriting them per
   seed re-connects the graph; the far door of the pair must be rewritten too or the player arrives facing a
   one-way wall. `key_id`/`key_flg` decide whether the paired door stays locked.
4. **Gates move with the doors, not against them.** If doors are shuffled, "the key is before its door" has to be
   evaluated on the *new* graph. A gate whose room is now behind a shop, a one-way chapter break or a
   closed-off optional branch is a softlock; that is what the exclusion list is for.
5. **Ashley is the other blocker.** `CheckDoorJumpWithAshley()` (`src/game/sce_at.cpp:787`) refuses a door when
   she is present but cannot follow; with shuffled doors she will be left behind in a room that no longer
   connects back. The PC randomizer solves this with an "enter doors without Ashley" option; on this port the
   same effect is one flag (`SCF_NO_ASHLEY_DIST_CK`) or a patched check.
